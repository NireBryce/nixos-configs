# Lessons from the den → flake-parts port, 2026-08-08

Companion to `2026-08-08-PORT-PLAN-(COMPLETED).md`, which records *what* was
done and where the plan was wrong. This one records how the work went wrong in
the doing, because none of that is recoverable from the tree or the commits.

Written for the next instance. The technical traps live in `CLAUDE.md`; these
are about method.

---

## 1. Every tool written during this port was wrong on its first run

Three for three. In each case the tool reported success.

| tool | first-run defect | how it surfaced |
|---|---|---|
| `unwrap.py` (2c, 151 files) | silently skipped `sops.nix`, whose declaration ends in `=` with the body on the next line — would have dropped its `config` argument | printed a sample of output instead of trusting `151 ok, 0 skipped` |
| `modules.py orphans` | reported eight nested categories as dead, because `collectModules` recurses and a module in `langs` is also collected by `development` | the output was implausible on its face |
| `host-fingerprint.nix` | said "no attribute in the fingerprint differs" for a change that moved the drvPath — it sampled home-file *names*, not content | tested it against a commit whose change it should have caught |

**The transferable part:** a summary line is not evidence. `151 ok, 0 skipped`
was true and useless — the file it mishandled was counted as OK. What caught it
was printing actual output for the three files known to be unusual.

`unwrap.py` now asserts its rewritten-declaration count against a looser pattern
and refuses the file on mismatch. Build that kind of check in from the start;
the failure mode here is silence, not error.

**Test a checker against a case it should catch.** The collision check was
verified by renaming `boot-durandal.nix` back to `boot.nix`, confirming the
report, and restoring. A check nobody has seen fail is not known to work.

## 2. When a tool contradicts you, suspect yourself first

Twice I concluded a tool was broken and was wrong both times.

- `diff-config.sh` reported IDENTICAL comparing against `HEAD~2`, which I
  believed predated a config change. It did not — an interleaved
  `claude settings change` commit meant `HEAD~2` was not the commit I assumed.
  The tool was right. Checked by evaluating both refs directly before touching
  anything.
- A `zsh -f -c` test appeared to show that aliases do not chain, which would
  have meant `ls` lost its eza flags. The test was invalid: **zsh expands
  aliases at parse time**, so an alias defined and used in the same command was
  never going to work. Re-run with the usage behind `eval`, both zsh and bash
  chain fine.

Cost of getting the second one wrong: I would have "fixed" `ls` by adding an
explicit alias, which *breaks* the chain and drops three flags. The intuitive
repair was the regression.

## 3. Writing a trap down does not stop you walking into it

`CLAUDE.md` gained a section on reading generated dotfiles. Within minutes of
writing it I hit both halves:

- queried `home.file.".zshrc"` and got zero starship hits. The attribute is
  `"./.zshrc"`. A wrong name returns **empty rather than erroring**, which is
  indistinguishable from a real negative.
- then `.bashrc` also came back empty, and I briefly believed I had caused a
  regression. `.bashrc` has no `.text` at all; it is built from `.source`. The
  content lives in `programs.bash.initExtra`.

Both are now in `CLAUDE.md` *and* in the `just dotfiles` recipe, because the
right fix is a tool that makes the mistake impossible, not a warning.

## 4. Bugs serialise, exactly as the handoff promised

`SESSION-HANDOFF.md` §3 said four bugs had hidden behind one another on the
sibling branch. Four more did here, each invisible until the phase before it
landed:

```
2c → .blerc declared twice; blesh.nix declared its module twice
2d → `boot` was both a category and a module name
2e → jq and bitwarden: nixos modules full of home-manager options
HM → programs.bash.blesh.enable, an option Home Manager has never had
```

The planning consequence: **a defect count derived from static analysis is a
lower bound.** The plan said eight and it was twelve.

## 5. Cross-module side effects are invisible without a fingerprint

Removing fish — an unused shell — also removed the man page index, because
`fish.nix:683` sets `programs.man.generateCaches = lib.mkDefault true` inside
`mkIf cfg.generateCompletions`. Nothing in this repo mentions `programs.man`.
Nothing in the fish module's *name* suggests it. `apropos` would have stopped
working with no visible cause.

`just diff` reported `homeFileHashes: removed '.manpath'` and that was the whole
thread. **Run it across any change that removes a module**, however unrelated
the module seems.

The same tool caught a comment-only edit shipping fourteen lines into
`~/.zshrc`: `#` inside a `''` string is shell text, not a Nix comment, so
config-maintenance notes were being emitted into the user's rc file.

## 6. Reading upstream source settled things guessing would have got wrong

Every one of these changed a decision:

- `flake-parts/extras/modules.nix:33` — `flake.modules` is
  `lazyAttrsOf (lazyAttrsOf deferredModule)` at the **top level**, and the only
  `freeformType` in flake-parts is on the `flake` option. That is why 151 files
  could not keep `flake.modules` inside `perSystem`.
- `home-environment.nix:626-628` — `home.shellAliases` feeds bash, zsh and fish.
  That is the cross-shell alias mechanism; there is no other.
- `home-environment.nix:322` — `home.sessionPath` is `listOf str`, so duplicate
  definitions concatenate. That is why every PATH entry appeared twice.
- Home Manager has **no blesh module at all**, so `programs.bash.blesh.enable`
  had never applied.
- `man-db 2.13.1 --help` — `--user-db` exists and, without `--create`, updates
  incrementally. The whole man-cache design depended on that being true.
- `nixos/modules/misc/man-db.nix` — `documentation.man.generateCaches` only maps
  `/run/current-system/sw/share/man`, so it would never index the Home Manager
  profile. Without reading it, "surely there's a NixOS way" would have produced
  a change that cost a rebuild and fixed nothing.

## 7. Verify the mechanism before betting a refactor on it

Before committing to repairing `dirsAsCategory` rather than replacing it, the
risky part — reading `config.flake.modules.<class>` from a file that also
*defines* an attribute in it — was modelled with flake-parts' own option type
and `apply`, and evaluated. It resolved cleanly, excluded `micro` from `nixos`,
and applied the imported config.

That is the same thing the sibling instance did before recommending the opt-in
pattern. It is cheap and it is the difference between a recommendation and a
guess.

## 8. Commit hygiene, learned the hard way

- **A commit message must not describe state that does not exist.** One message
  referred to a `PORT-PLAN.md` note that had not been written yet; the next
  commit had to make it true. The sibling session hit the identical trap.
- **Check what is staged before writing the message.** One commit swept all 24
  `dirsAsCategory` files in alongside a two-file rename, and the message
  described only the rename. Split with `git reset --soft`.
- Staging early (`git add` before `nix eval`, which flakes require) makes this
  easy to do by accident.

## 9. Decisions belong to the user, and the record may already exist

The `dirsAsCategory` question — repair or replace with per-module opt-in — was
settled by finding the original exchange in a previous session's transcript
(`~/.claude/projects/*/[uuid].jsonl`), not by re-deriving it. The user had
already approved the opt-in pattern on the sibling branch, *and* had separately
built categories here on purpose. Those look contradictory until you find that
the roster-readability objection came **after** adoption and was answered with a
script rather than a reversion.

Worth knowing that transcript archaeology is available. Worth knowing more that
the user's own history is a better source than inference.

## 10. Honest reporting, specifically

Nothing in this repository has ever been built or switched. Every "verified"
claim means *evaluates and produces the expected derivation*. The single
exception is `checks.<system>.module-tree`, which is static and does build on
darwin — it is the only thing in the entire port that has actually run.

Say which of those you mean, every time. "It works" is not available here.
